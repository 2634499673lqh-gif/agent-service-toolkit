# T048 — Bounded retry

Depends on: T047. Implementation Model: STANDARD; Review: Strong Review.

## Objective and scope

Implement exactly one retry budget, serializing `retry_count` in AgentState. Required scenarios: fail once → retry → succeed → verify PASS → T035 succeed_run; always fail → exhaustion → T035 fail_run. Retry is not HTTP idempotency and creates no TaskRun.

## Acceptance / security / transaction / tests

Tests cover success-after-retry, exhaustion, counter persistence, and no infinite loop. Runtime validates tenant-scoped Task/Run before T035 transitions and never mutates statuses directly. Use discrete service transactions; no DB transaction spans execution. Add focused deterministic tests and docs; no Codex commit/push.

## Governance

Affected layer: runtime recovery and T035 integration. Tenant validation precedes execution. Required tests include deterministic recovery and lifecycle assertions; PostgreSQL evidence is required where lifecycle/concurrency behavior is exercised. Strong Review is required.

## Frozen counter semantics

`RETRY_BUDGET = 1`; `retry_count` starts at `0`. The initial execution is not
a retry. On RETRY, if `retry_count < 1`, increment to `1` before routing back
to executor; otherwise route terminal failure. The retry stays inside the
same RUNNING TaskRun, never decreases, and never resets after replan.
