# T023 — Opaque authentication session/token service

Implementation Model: STANDARD  
Review Model: STRONG_REVIEW_REQUIRED

Implement login and credential issuance using ADR-004 opaque server-side sessions. Do not implement general authorization dependencies or change shared bearer compatibility.

## Depends on

T021, T022, and T022A.

## Scope

Add approved `pwdlib[argon2]` only after review. Use Argon2id verification, generic login failure, opaque token from at least 32 random bytes, SHA-256 hash-at-rest with indexed lookup, UUID4 session ID, 24-hour expiry, explicit revocation, and expired-session cleanup. Bind a session to user + membership; revalidate active state on every request. Add the controlled CLI/setup bootstrap contract: hidden interactive password prompt twice via `getpass`-equivalent, reject `--password` and positional plaintext password, and never log password/hash. First bootstrap creates Organization + User + owner Membership in one business transaction. Exact complete active owner state is an already-initialized no-op without duplicate rows or password reset. Partial/conflicting/inactive/mismatched state fails closed, non-zero, and never repairs, overwrites, changes password, or elevates role. No global consumed flag; no HTTP registration.

## Verification

### Frozen membership selection contract

Read ADR-004's **T023 membership selection addendum — frozen 2026-09-16** before implementation. Use `async login(email: str, password: str, *, organization_id: UUID | None = None) -> AuthenticatedSession | OrganizationSelectionRequired`. Preserve successful `AuthenticatedSession` fields. The immutable selection result has only `code = "ORGANIZATION_SELECTION_REQUIRED"` and `organization_ids: tuple[UUID, ...]` (eligible IDs deduplicated and sorted by canonical UUID string); it has no token or session and grants no access. Do not invent an HTTP mapping or chooser credential.

Canonicalize email, authenticate password and active User first, then query that User's memberships and verify ownership, active Membership and active existing Organization. Count only eligible rows. No selector: zero fails generically, one issues, more than one requires selection without choosing a default. A active/B inactive selects A if its Organization is active. A supplied organization selector must match a verified eligible Membership; invalid/malformed/foreign/inactive/nonexistent selectors fail generically without fallback or metadata. Unknown email, wrong password and inactive User always produce the existing `Invalid credentials` error. Client membership IDs and roles are not accepted selection inputs.

Selection resubmission and organization switching both require a fresh credential login and fresh server checks, issuing a new session for the verified Membership. Never mutate the prior session's scope; prior sessions persist until explicit revocation or expiry. No CurrentPrincipal work is included.

### Selection acceptance cases for subsequent implementation

- Replace the multi-membership failure expectation in `tests/service/test_auth_session.py::test_login_requires_exactly_one_active_membership`: zero eligible still fails, multiple eligible yields the typed selection result and no token generation/session write.
- Test one eligible success; A active/B inactive auto-selects A; exclude active memberships whose Organization is inactive or missing before counting; zero eligible fails generically.
- Test explicit selection of each eligible organization for the same multi-org User and exact AuthSession user/membership binding. Input ordering and role do not choose a default.
- Test unknown/malformed selector, foreign user's membership, inactive membership and inactive/missing Organization: same external failure and no write/list. Test ownership defensively with a repository stub returning a foreign row. Fixtures must not silently invent active Organizations for nonexistent IDs.
- Test unknown email, wrong password and inactive User with/without selectors: no organization metadata or membership lookup; selection-required is reachable only after successful authentication.
- Test selection result contains only eligible UUIDs and the fixed code, deterministic order, no token/password/hash/role/membership metadata, and no sensitive result logging.
- Test fresh resubmission rejects a membership deactivated since selection, rechecks password, and cannot use the selection result as a credential. Switching issues a distinct session while preserving the old session's membership and revocation state.
- Run focused `uv run pytest tests/service/test_auth_session.py -q`, existing T023 tests, then the existing authentication full-pytest/Strong Review gate. These are future implementation checks, not tests claimed by this documentation decision.

### Existing authentication and bootstrap verification

Test valid/wrong/unknown/inactive login, generic errors, expiry, revocation, tampering/replay, hash/token redaction, hidden prompt use, rejection of plaintext CLI arguments, successful bootstrap, exact repeated no-op (no duplicate/no password reset), partial/conflicting fail-closed behavior, intermediate-failure full rollback, and plaintext/hash absence from logs. Full pytest is required at the authentication gate.

## Forbidden

No JWT, role claims as authority, refresh-token family, SSO, email verification/change, or `AUTH_SECRET` behavior change. `/api/v1` does not accept legacy bearer as a TaskPilot principal.
