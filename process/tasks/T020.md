## Required decisions and output

Record an accepted ADR plus implementation-ready T021–T027 cards covering:

1. **Identity topology:** compare one-organization-per-user with User–Organization Membership. Select the minimum that supports tenant isolation, future task ownership, approval authorization, organization knowledge, user memory, demo setup, and future extension. Define whether a user may have more than one active membership and how an active organization is selected.
2. **Role policy:** compare a small role enum plus explicit server-side policy (for example `owner`, `admin`, `member`) with normalized roles/permissions tables. Select the minimum V1 model and enumerate every protected operation. Do not create an enterprise policy engine.
3. **Trust invariant:** authorization context must be derived as credential → authenticated user → server-derived membership/org/role. Client `user_id`, `organization_id`, role claims, `agent_config.user_id`, `/threads` query values, and AG-UI forwarded configurable values must never select authorization scope. Classify current upstream endpoints as compatibility-only, quarantine them, or adapt them in a later card.
4. **Persistence/migrations:** decide SQLAlchemy/Alembic (or a justified alternative), sync/async access, PostgreSQL business schema, SQLite support, shared database versus separate database, schema namespace, revision ownership, fresh-database order, LangGraph `setup()` ordering, production auto-migrate policy, test DB strategy, downgrade policy, and how business sessions/transactions are provided by FastAPI. LangGraph internal tables must remain outside TaskPilot migrations.
5. **Identifiers and lifecycle:** choose one ID type for User, Organization, Membership and auth records; define API exposure and test implications. Define UTC timestamps, `created_at`/`updated_at`, active/inactive behavior, deletion policy, FK/cascade rules, and prohibition of silent cascade for audit-critical data.
6. **Email/bootstrap:** decide login identifier, normalization/case rules, uniqueness scope, inactive/duplicate behavior, no anonymous self-registration, and a controlled first organization/admin bootstrap path (CLI/seed/setup command/test fixture).
7. **Authentication:** compare signed JWT with server-side opaque session/token. Choose one and specify algorithm/key source if JWT or storage/hash/expiry/revocation if opaque. Define expiration, claims trust, inactive-user behavior, revocation, browser compatibility, and separation from current optional `AUTH_SECRET`; decide how legacy bearer auth remains compatibility-only.
8. **Password security:** if password login is selected, choose an existing suitable library/dependency after inspection; require non-reversible hashing, constant-time verification, generic login failures, no plaintext/hash in logs/API, and fake test credentials only.
9. **Authorization/error policy:** define authenticated-user, membership, role, resource-tenant ownership, allow/deny rules; cross-tenant behavior (prefer consistent 404 when hiding existence); approval authorization; and server-side checks for every future repository query.
The ADR must state one final answer for every comparison above, freeze role semantics and the cross-tenant 403-versus-404 rule, and name exact implementation files. It must assign session lifecycle/transaction ownership to T021/T022 (session factory and repository boundary), with T024 consuming that boundary; ORM sessions must never enter LangGraph `AgentState`.

10. **Acceptance matrix:** specify tests for valid/invalid/inactive login, credential expiry/revocation, same-tenant allow, cross-tenant deny/404, forged IDs/claims, unauthorized approval, duplicate decisions, secret redaction, migration isolation, rollback and transaction cleanup.

## Constraints

Do not modify `AUTH_SECRET` behavior in this task. Do not add dependencies or tables. Do not trust upstream conversation `user_id` as business identity. Do not silently rewrite the roadmap; record numbering drift only.

## Acceptance criteria

- [ ] ADR names the selected options and rejected alternatives with V1 tradeoffs.
- [ ] Exact schema fields, constraints, indexes, state/lifecycle rules, and ownership boundaries are fixed for T021/T022.
- [ ] Authentication and authorization invariants are explicit and testable.
- [ ] T021–T027 cards name exact files, dependencies, forbidden scope, focused commands, security tests, docs, and rollback/compatibility notes.
- [ ] Migration cards require fresh/existing upgrades, metadata/version verification, LangGraph coexistence, and downgrade policy; model-only tests are insufficient.
- [ ] If Membership is selected, create `T022A` or explicitly define a bounded membership subtask in T022; the implementer may not invent the split.
- [ ] No production code, migration, dependency, or `AUTH_SECRET` behavior changes.
- [ ] `process/PROGRESS_LOG.md` records evidence, limitations, learner notes, and next task.
