# T093 — Correlation propagation

Depends on: T091, T092. Review: Strong Review.

## Objective

Connect one observable execution from its request source through Task, TaskRun,
step coordinates, AgentRun, and ToolCall.

## Required contract

- HTTP-bound AgentRun records require the UUID generated by the existing
  request middleware. Internal work may have request_id = NULL; incoming
  headers, checkpoints, and model output are never authoritative.
- task_run_id is required and comes from the tenant-validated durable TaskRun.
  task_id is derived through the TaskRun -> Task join, not stored in trace rows.
- Phase 7 has no persisted TaskStep. Use zero-based
  (replan_count, step_position) and the existing bounded retry_count; do not
  invent a task_step_id.
- AgentRun and ToolCall IDs are server-generated UUIDs. ToolCall inherits all
  parent correlation through AgentRun.
- An existing Approval ID may be exposed only as a tenant-scoped,
  response-only relation for the same run/replan/step tuple.

The minimum reconstruction path is
request_id -> task_id -> task_run_id -> (replan_count, step_position,
retry_count) -> agent_run_id -> tool_call_id. All identifiers are
observational and never authorization credentials.

## Acceptance and negative evidence

Deterministic end-to-end assertions prove required/optional identifiers,
middleware propagation, retry/replan coordinates, missing-ID NULL behavior,
and rejection of caller/checkpoint/model authority. Correlation must not alter
authorization or lifecycle transitions.

## Documentation and checks

Update observability/API documentation and run focused tests, static checks,
and git diff --check during implementation.
