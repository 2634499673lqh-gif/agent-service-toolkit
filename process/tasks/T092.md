# T092 — ToolCall persistence

Depends on: T090. Review: Strong Review.

## Objective

Persist one bounded, sanitized dispatch-attempt observation beneath an
AgentRun.

## Required contract

Implement the ToolCall table exactly as specified in ADR-009:

- UUID id is the server-generated tool_call_id.
- agent_run_id is the only ownership foreign key and uses ON DELETE RESTRICT;
  TaskRun and tenant are derived through AgentRun.
- call_index starts at 0, is at most 999, and is unique per AgentRun:
  UNIQUE(agent_run_id, call_index). A repeated dispatch is a new row.
- tool_name is server-selected, non-blank, and at most 128 characters;
  tool_version is optional and at most 64 characters.
- Status is one of running, succeeded, failed, or unknown; it is
  observational and never a TaskRun state.
- Arguments are a required sanitized JSON object of at most 8,192 compact
  UTF-8 bytes. Result is an optional sanitized JSON object with the same bound.
  Error, UTC timing, duration, usage, and row timestamps use ADR-009 bounds.

Do not store tenant/task duplicates, credentials, raw provider responses,
unbounded documents, checkpoints, prompts, or context.

## Transaction and SQL requirements

Repositories flush only and leave commit/rollback to the service transaction.
All reads use the AgentRun -> TaskRun -> Task tenant join in SQL. Foreign
parents and cross-tenant rows are invisible; parent deletion is restricted.

## Acceptance and negative evidence

Migration up/down, PostgreSQL foreign-key/uniqueness/bounds tests, cross-tenant
read tests, duplicate call tests, rollback tests, and secret-bearing
arguments/results redaction tests are required. Redaction tests belong to T092,
not T098.

## Documentation and checks

Update the database/observability docs and run focused tests, static checks, and
git diff --check during implementation.
