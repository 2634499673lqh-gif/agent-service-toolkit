## Decisions

1. **Parameter authority.** Before any model parse, a deterministic server
   extractor scans the original user text for only `cloud_threshold` and
   `decline_threshold`. Supported forms are a decimal number adjacent to a
   supported parameter phrase (`maximum ... cloud ... threshold ... 30%` or
   `NDVI decline threshold ... -0.15`); no generic NLP or model-provided
   `explicit` flag is trusted. The extractor returns trusted `{value, source:
   user_text}` evidence, or `explicit: false`. A valid extracted value takes
   precedence over the deterministic server default. Missing values use fixed
   defaults (`cloud_threshold=30.0`, `decline_threshold=-0.2`). Malformed,
   out-of-range, unsupported-unit, or conflicting repeated explicit values are
   rejected deterministically and never replaced by model output. The LLM may
   extract dates and semantic intent only; effective values record
   `user_text` or `server_default`.
2. **Execution/data mode.** `data_mode`, live/fake provider switches, fixture
   selection, and runtime profile are server-owned policy. Model output cannot
   select a mode or provider. Unsupported or conflicting model values fail closed.
3. **Planner/provider evidence.** Reuse AgentRun provider metadata and existing
   sanitized error fields plus TaskRun `result_metadata` for a bounded stage
   summary. Persist provider/model, live/fake flags, start/end, error class/code,
   and request identifier when available. Never persist keys, raw request bodies,
   unrestricted transcripts, or tracebacks.
4. **Stage semantics.** The exact terminal result-metadata field is
   `stage_status`, a fixed object with exactly `planner`, `execution`, and
   `verifier` keys. Each value is one of `not_started`, `running`, `passed`,
   `failed`, or `not_run`; `not_started` means an active checkpoint has not
   entered that stage, while `not_run` means terminal execution skipped it after
   an earlier terminal failure. Terminal `stage_status` never contains
   `running`; active running status remains in existing TaskRun lifecycle and
   AgentRun/ToolCall observations. Explanation is not a separate graph stage:
   it is part of the `execution` capability output. The field is allowlisted,
   fixed-size, and bounded by the existing `result_metadata` byte limit.
5. **Live STAC normalization.** Network/provider failure is RETRY once when the
   bounded retry budget permits; malformed response is TERMINAL; no imagery is
   REPLAN only when an alternate bounded selection is valid; imagery violating an
   explicit user threshold is TERMINAL; imagery violating only a server default
   may REPLAN once within the default policy. Recovery may never relax an explicit
   threshold or other user constraint.
6. **Real raster fixture.** Prepare small, cached, real Sentinel-2 Red/NIR
   rasters for two validated scenes (candidate IDs are the Phase 12 live scenes;
   final IDs require acquisition verification). Use a compact non-proprietary
   format already supported or minimally supported by existing dependencies,
   with a manifest rather than large binary growth. Fixture size is bounded by a
   documented maximum and must remain suitable for repository/CI use.
7. **Provenance binding.** Every raster bundle manifest binds scene/item ID,
   acquisition date, collection, Red/NIR asset identity, AOI/bounds, CRS,
   resolution, fixture version, dimensions, and checksum. Runtime metadata and
   raster manifest must match exactly on the binding fields; mismatch fails closed.
8. **Raster authority.** NDVI, delta, areas, masks, and artifact bounds remain
   deterministic NumPy/server computations. LLM prose may explain validated
   evidence only. The real-pixel mode name is `CACHED_REAL_SENTINEL2_RASTER`;
   `REAL_STAC_LIVE_METADATA_LOCAL_FIXTURE` remains a historical Phase 12 mode.
9. **UX hierarchy.** Streamlit remains the product surface. The primary view
   presents request, interpreted bounded parameters, current stage, runtime
   profile, selected scenes, metrics, three artifacts, explanation, verification,
   provenance, and failure evidence. UUIDs and raw trace details move to an
   expandable technical section. All reads and mutations remain authenticated
   server API calls.
10. **Polling.** While a run is active, the UI may perform finite, bounded
    automatic refreshes with a fixed interval and maximum attempts, then stop
    with a truthful refresh action. No websocket, unbounded loop, or optimistic
    lifecycle state is introduced.
11. **Deterministic versus live evidence.** CI uses fake/provider-free models,
    cached real-pixel fixtures, and deterministic evaluation. Live DeepSeek and
    Earth Search are separate opt-in smoke evidence and never gate ordinary unit
    tests through network access.
12. **Exit evidence.** T145 requires deterministic evaluation, required
    PostgreSQL regression, affected full regression, static checks, recorded live
    smoke, provenance-bound real pixels, three artifacts, accurate stage/trace
    evidence, visible runtime profile, and portfolio documentation. No claim of
    scientific accuracy, production-scale remote raster processing, autonomy,
    or public SaaS readiness is permitted.
13. **Attribution and deferral.** Documentation separates upstream
    `agent-service-toolkit` capabilities from TaskPilot/GeoChange work. BYOK,
    credential management, billing, workers, distributed infrastructure, generic
    GIS/RAG/MCP/multi-agent systems, arbitrary AOIs, large assets, and React
    rewrite are deferred, not rejected. Later candidates are recorded only as a
    non-binding roadmap after T138.

## DAG and batches

`T138 → (T139, T141); T139 → T140; T141 → T142; (T140, T142) → T143 → T144 → T145`.

Technical dependencies permit T141 after T138 independently of T139/T140.
Execution policy remains sequential review batches: Batch A `T139 → T140`,
Strong Review, Batch B `T141 → T142`, Strong Review, Batch C `T143 → T144`,
Strong Review, then T145. T143 must complete before T144 begins.

## Deferred / rejected for this phase

No BYOK or organization credential store, billing/quota product, Redis/Celery/
Kafka/Kubernetes, public worker platform, React/Next rewrite, generic
multi-agent/RAG/vector/MCP marketplace, arbitrary AOI/geocoder, generic GIS
engine, production-scale COG pipeline, unrestricted remote raster processing,
large raster assets, or broad provider-management platform.

## Post-Phase-13 candidates (non-binding)

Possible later work includes organization-scoped provider settings/BYOK, public
deployment hardening, quota/cost controls, more validated AOIs and use cases,
robust raster acquisition/windowing, enhanced evaluation, MCP/RAG, durable
workers, and multi-agent decomposition only if demonstrated complexity justifies it.

## Supersession

This ADR narrowly supersedes Phase 12's use of synthetic local pixels as the
supported portfolio evidence and its implicit model-owned numeric defaults.
Existing Task/TaskRun lifecycle, tenant/security, checkpoint/replay, bounded
retry/replan, trace redaction, verifier authority, and Streamlit-first ADR-011
decisions remain frozen.
