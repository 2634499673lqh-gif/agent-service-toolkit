# ADR-009 — Phase 7 observability boundary

Date: 2026-09-24
Status: Accepted/frozen; Phase 7 Planning Strong Review APPROVED. T090–T097 implementation and review work is COMPLETE / APPROVED. T098 Phase 7 Final Audit is APPROVED. Phase 7 is COMPLETE. Phase 8 is NOT STARTED.

## Purpose and frozen boundary

Phase 7 stores the smallest durable evidence needed to reconstruct one
TaskPilot execution. The business database remains authoritative for Task,
TaskRun, lifecycle, tenant, approval, and business outcome. LangGraph
checkpoints remain recovery state. AgentRun and ToolCall rows are observation
records and never become authorization, lifecycle, approval, or checkpoint
authority.

External tracing, analytics/event buses, workers, billing, UI, evaluation, and
new lifecycle or authorization states remain deferred.

## Ownership, SQL scope, and transaction contract

The normalized ownership path is:

```text
ToolCall.agent_run_id
  -> AgentRun.task_run_id
  -> TaskRun.task_id
  -> Task.organization_id
```

`agent_runs` has a foreign key to `task_runs`; `tool_calls` has a foreign key
to `agent_runs`. Both use `ON DELETE RESTRICT`. Neither table stores
`organization_id` or a duplicate `task_id`. There is no second tenant
authority. Existing Tasks and TaskRuns already use `RESTRICT`, so deleting a
Task cannot silently erase its observability evidence. No public hard-delete
operation is added by Phase 7; retention or archival requires a later
decision.

The tables live in the existing PostgreSQL-only `taskpilot` schema and use the
existing Alembic ownership. Every tenant-visible read, including T097, joins
through the path above and applies the server-derived principal organization
predicate in the same SQL statement. A global query followed by Python tenant
comparison is forbidden.

Repositories may add and flush rows but never commit, roll back, close, or
replace the caller's `AsyncSession`. The service that owns the operation owns
the transaction. A trace write made in that transaction is durable only when
the containing transaction commits; a persistence error propagates and rolls
back that transaction rather than leaving a partial trace. Observability does
not open a second transaction or hold a business transaction across graph or
checkpoint execution.

All timestamps are timezone-aware PostgreSQL `timestamptz` values normalized to
UTC. Row `created_at` and `updated_at` follow the existing Task/TaskRun server
defaults. Event `started_at` is required, `finished_at` is optional, and
`finished_at` cannot precede `started_at`. `duration_ms` is a nullable,
non-negative integer number of milliseconds. A missing duration is `NULL`,
never zero.

## T091 — AgentRun persistence contract

One AgentRun row represents one server-selected agent/node invocation for one
logical plan slot and retry attempt. The implementation must provide these
columns and constraints (names may use the repository's normal SQLAlchemy
style, but their meaning is fixed):

| Field | Contract |
|---|---|
| `id` | Server-generated UUID primary key; the canonical `agent_run_id`. |
| `task_run_id` | Required UUID foreign key to `task_runs.id`, `RESTRICT`; ownership is resolved through the Task join. |
| `request_id` | Nullable UUID. Required when the invocation is inside an HTTP request; sourced from the request middleware, never from a caller header. `NULL` means no request source was available. |
| `replan_count` | Required integer `0..1`, copied from the validated runtime state. |
| `step_position` | Required integer `0..7`, zero-based persisted position. Runtime `PlanStep.position` is one-based, so persistence stores `position - 1`; this is the same slot convention used by Approval. No `TaskStep` row or synthetic `task_step_id` is created. |
| `retry_count` | Required integer `0..1`, copied from the validated runtime state. It identifies the bounded initial attempt (`0`) or retry (`1`). |
| `agent_name` | Required non-blank server-selected node label, maximum 128 characters. It is observational metadata, not a registry or caller authority. |
| `status` | Required observational value: `running`, `succeeded`, `failed`, `waiting_approval`, or `unknown`. It never changes `TaskRun.status`. |
| `error_class` | Nullable `RETRY`, `REPLAN`, `TERMINAL`, or `UNKNOWN`; non-null only when the invocation did not complete normally. |
| `error_code` | Nullable non-blank string, maximum 64 characters; use the existing normalized runtime code. |
| `error_message` | Nullable sanitized string, maximum 500 characters; raw exception text, stack traces, prompts, credentials, and tokens are forbidden. |
| `started_at` / `finished_at` | Required UTC start and optional UTC finish. A non-terminal or interrupted observation may have no finish. |
| `duration_ms` | Nullable non-negative integer milliseconds, derived only from the two event timestamps. |
| `usage` | Nullable bounded normalized usage object defined by T095. When an adapter ran, it stores either the known shape or the explicit unavailable shape; `NULL` means no usage observation was applicable. It is never an all-zero placeholder. |
| `provider_metadata` | Nullable allowlisted JSON object, compact UTF-8 maximum 2,048 bytes; provider/model identifiers only, never prompts, credentials, or raw responses. |
| `created_at` / `updated_at` | Required UTC row timestamps using existing Task/TaskRun conventions. |

The canonical uniqueness constraint is:

```text
UNIQUE (task_run_id, replan_count, step_position, retry_count, agent_name)
```

This prevents duplicate evidence for one server-selected node invocation while
allowing the next retry or replan to be a distinct observation. `id` remains
the external correlation identity; the tuple is the durable idempotency key.
The repository must resolve the parent TaskRun in the trusted tenant scope
before insert and must not accept a tenant field from the caller.

## T092 — ToolCall persistence contract

One ToolCall row represents one dispatch attempt made by one AgentRun. A
repeated dispatch is a new `call_index` and row; an earlier failed row is not
overwritten. The implementation must provide:

| Field | Contract |
|---|---|
| `id` | Server-generated UUID primary key; the canonical `tool_call_id`. |
| `agent_run_id` | Required UUID foreign key to `agent_runs.id`, `RESTRICT`; TaskRun and tenant are derived through the parent. |
| `call_index` | Required non-negative integer, starting at `0` for each AgentRun and maximum `999`; assigned by trusted server code. |
| `tool_name` | Required non-blank server-selected name, maximum 128 characters. |
| `tool_version` | Nullable bounded version string, maximum 64 characters. |
| `status` | Required observational value: `running`, `succeeded`, `failed`, or `unknown`; it is not a TaskRun state. |
| `started_at` / `finished_at` | Required UTC start and optional UTC finish; finish cannot precede start. |
| `duration_ms` | Nullable non-negative integer milliseconds. |
| `arguments` | Required sanitized JSON object, compact UTF-8 maximum 8,192 bytes. Secret-bearing keys and values are redacted before persistence. |
| `result` | Nullable sanitized JSON object, compact UTF-8 maximum 8,192 bytes; raw provider responses and arbitrary documents are not stored. |
| `error_class` / `error_code` / `error_message` | The same bounded error contract as AgentRun. |
| `usage` | Nullable T095 usage object. A provider that cannot return usage stores the explicit unavailable shape; `NULL` means no usage observation was applicable. |
| `created_at` / `updated_at` | Required UTC row timestamps using existing conventions. |

The canonical uniqueness constraint is:

```text
UNIQUE (agent_run_id, call_index)
```

The T092 persistence tests own the negative redaction and payload-boundary
cases. A ToolCall inherits `request_id`, `task_id`, `task_run_id`, step
coordinates, and tenant only through its AgentRun; those values are never
accepted as duplicated caller authority.

## T093 — Correlation contract

The minimum reconstructable path is:

```text
request_id (when an HTTP source exists)
  -> task_id (derived from TaskRun -> Task)
  -> task_run_id
  -> (replan_count, step_position, retry_count)
  -> agent_run_id / agent_name
  -> tool_call_id / call_index
```

Identifier sources and propagation are fixed:

| Identifier | Requiredness and authoritative source |
|---|---|
| `request_id` | Required for HTTP-bound AgentRun records and optional for internal/background work. The request middleware generates it and stores it in request state/context; the incoming header is not authority. ToolCall inherits it. |
| `task_id` | Required for reconstruction but not duplicated in trace rows; derived by the server's `TaskRun -> Task` join. |
| `task_run_id` | Required on AgentRun and comes from the tenant-validated durable TaskRun. It is never taken from checkpoint or caller data. |
| `task_step_id` | Not required and unavailable in Phase 7 because TaskStep persistence is deferred. The required step representation is the zero-based `step_position` plus `replan_count`; no synthetic ID is generated. |
| `agent_run_id` | Required server-generated AgentRun primary key. |
| `tool_call_id` | Required server-generated ToolCall primary key; ToolCall is reached through `agent_run_id`. |
| `approval_id` | Optional response-only relation when an existing Approval matches the same run/replan/step tuple; sourced from the tenant-scoped Approval row and never used for authorization. |

Correlation IDs are observational labels only. They cannot authorize a read,
select a tenant, resume a checkpoint, or approve an action. A missing optional
identifier is returned as `NULL`/`unavailable`; it is never guessed or replaced
with a zero value.

## T094 — Timing, status, error, and recovery contract

T094 normalizes evidence without introducing a second Task/TaskRun lifecycle
machine:

* timestamps are UTC-aware ISO 8601 values at API boundaries and `timestamptz`
  in PostgreSQL;
* durations are integer milliseconds, nullable when either endpoint is
  unavailable, and bounded to `0..86_400_000` (24 hours) per row;
* the status vocabularies are the observational values in T091/T092 only;
  TaskRun lifecycle remains the existing `pending/running/succeeded/failed/
  cancelled` contract;
* `error_class`, `error_code`, and sanitized `error_message` use the bounded
  fields above. `UNKNOWN` is used when a source cannot classify an error;
  absence of an error is `NULL`, not `UNKNOWN`;
* retry and replan are represented by the AgentRun coordinates and adjacent
  rows: a retry increments `retry_count` within the same replan, and a replan
  increments `replan_count` and starts at `step_position = 0`. The prior row's
  normalized error remains immutable evidence;
* missing timing or error data remains `NULL`/`UNKNOWN`. No adapter infers a
  success, zero duration, terminal failure, or retry from absence alone.

## T095 — Provider usage contract

The normalized usage value is one of these two shapes:

```json
{"status":"known","input_tokens":123,"output_tokens":45,"total_tokens":168,
 "cached_input_tokens":0}
```

or:

```json
{"status":"unavailable","reason":"not_returned"}
```

`reason` is one of `not_returned`, `unsupported`, or `malformed`. Token counts
are integers in `0..1_000_000_000_000`; optional `cached_input_tokens` has the
same bound. When a provider omits `total_tokens`, the adapter may derive it as
`input_tokens + output_tokens` only when both are present and within bounds.
Any missing, malformed, negative, or out-of-bound value produces the
`unavailable` shape. The unavailable shape is persisted and returned as an
explicit reason; it is never changed to numeric zero. A nullable usage field is
reserved for a record where no usage observation was applicable. Provider
metadata is limited to allowlisted provider/model/response
identifiers and the 2,048-byte bound above.

## T096 — Deterministic cost-estimate contract

Pricing is an explicit in-process configuration, not a remote lookup or billing
ledger. A pricing entry is keyed by `(provider, model, version)` and contains:

```text
provider: non-blank string <= 64
model: non-blank string <= 128
version: non-blank string <= 32
input_price_per_1k: non-negative Decimal with at most 12 integer and 6 fractional digits
output_price_per_1k: non-negative Decimal with at most 12 integer and 6 fractional digits
currency: non-blank string <= 8
```

The pure estimator accepts only known usage and a matching entry. It computes
`input_tokens / 1000 * input_price_per_1k + output_tokens / 1000 *
output_price_per_1k`, rounds the result to six fractional places with
`ROUND_HALF_UP`, and returns the currency plus a fixed-scale decimal string.
Token counts remain bounded by T095; a result above `10^18` currency units is
an `unknown` overflow result. Missing/unsupported pricing and unavailable or
partial usage return a deterministic `unknown` result with exactly one reason:
`missing_price`, `unsupported_model`, `usage_unavailable`, or `overflow`.
Unknown is not represented as numeric zero. The estimate is informational and
must not be used as billing truth.

## T097 — Tenant-safe timeline query contract

The planned read is `GET /api/v1/tasks/{task_id}/runs/{run_id}/trace` with an
optional `limit` defaulting to `100` and capped at `500`. A visible run with no
trace rows returns `200 []`; no global trace list is exposed. Every SQL query
must constrain `Task.id = :task_id`, `TaskRun.id = :run_id`,
`TaskRun.task_id = Task.id`, and `Task.organization_id =
:principal_organization_id`, then join AgentRun and ToolCall through their
foreign keys. Tenant filtering happens before projection and pagination.

Authentication and visibility follow the frozen API conventions: missing,
malformed, expired, revoked, or inactive credentials return generic `401` with
`WWW-Authenticate: Bearer`; a nonexistent or cross-tenant Task/TaskRun is
`404 Not Found`; an authenticated active member of the visible tenant may read
the timeline, matching existing TaskRun inspection, so this read has no extra
role gate and does not manufacture a `403`. If a later explicitly role-gated
operation is added, it must use the existing `403 Forbidden` helper without
changing the cross-tenant `404` rule.

The response is an allowlisted projection containing correlation IDs,
server-selected names, status, UTC timing, duration, normalized error fields,
usage, estimate result, and bounded sanitized metadata. It excludes raw
checkpoints, prompts, context, credentials, authorization objects, raw
provider responses, and unbounded arguments/results. T097 applies the existing
recursive redaction helper again at the response boundary; its tests own the
response-redaction and cross-tenant visibility cases. No Python-side tenant
comparison is an authorization check.

Stable order is:

```text
started_at ASC,
event_kind_rank ASC (AgentRun = 0, ToolCall = 1),
agent_run_id ASC,
call_index ASC (NULL for AgentRun),
event_id ASC
```

The tuple is deterministic even when timestamps tie. Failure, retry, and
replan reconstruction uses each immutable AgentRun row's
`(replan_count, step_position, retry_count, status, error_*)` and its ToolCall
children; the query must not collapse attempts to only the latest row.

## DAG and audit ownership

`T090 → (T091, T092) → T093 → (T094, T095) → T096 → T097 → T098`.

T098 is exclusively the Phase 7 Final Audit: fresh-eyes, independent,
read-only, non-mutating, and no test/code fixes, commit, or push. It audits
the evidence produced by T091–T097, including the redaction tests owned by
T092 (persistence payloads) and T097 (timeline response). No T099 is created.
