# ADR-014 — Phase 14 Geo Analysis Skill Expansion

Date: 2026-10-02  
Status: **Accepted / frozen**. This design freeze
authorizes no production code, migration, fixture, dependency, or UI change.

## Scope and authority

ADR-013 remains accepted and frozen. The current supported analysis is
`vegetation_change` with `NDVI`, using the existing confirmed-intent,
TaskRuntimeService, Runtime graph, deterministic verifier, TaskRun metadata and
Streamlit contracts. This proposal extends the model to `water_change` and
`urban_change` without redesigning the Agent Runtime or adding RAG, a vector
database, Memory Service, plugin discovery, or a generic GIS engine.

## 1. Skill and Runtime

The Skill contract is static and code-owned. It is the single source of truth
for indicator pairing, allowed capabilities, required order, result type and
artifact names:

| analysis_type | indicator | current allowed order |
|---|---|---|
| `vegetation_change` | `NDVI` | `resolve_aoi → search_sentinel2 → compute_vegetation_change → summarize_change` |
| `water_change` | `NDWI` | pending the 3B data gate |
| `urban_change` | `NDBI` | pending the 3C data gate |

On every new start and every resume, the server derives the selected Skill from
the validated `Task.confirmed_intent.analysis_type` and resolves it through
this static specification. The checkpoint is recovery state only: it cannot
select, replace, or authorize a Skill or capability. There is one minimal
static specification for these constraints; Planner output, checkpoint data,
and capability output cannot create a second source of Skill authority.

The existing CapabilityDispatcher, Planner, Executor and Verifier remain the
execution framework. `TaskRuntimeService` owns authentication, tenant scope,
lifecycle, transactions, checkpoint identity and final persistence. A Skill
owns only typed inputs, step constraints, deterministic calculation, evidence
binding and result validation.

Planner output and replan must validate against the Skill selected by the
server from the persisted, validated `Task.confirmed_intent`; checkpoint resume
derives that Skill again from the same Task record. The Skill specification is
static and code-owned, while only `Task.confirmed_intent` is persisted. Unknown
analysis types, unknown or cross-Skill capabilities, wrong order, wrong
indicator, and result-type mismatches fail closed. Capability registration
alone never grants permission; candidate output cannot replace Runtime stage
status or verifier truth.

## 2. Intent and compatibility

`Task.confirmed_intent` remains nullable JSONB, bounded to 4096 bytes. New
intent branches are strict, analysis-specific models with `extra=forbid` and
server-owned policy fields. Existing `vegetation_change` JSON/defaults remain
unchanged: `Sentinel-2`, cloud threshold 30.0, decline threshold -0.2,
Wuhan East Lake, and ordered non-overlapping periods.

Tasks with a non-NULL `confirmed_intent` use strict Skill routing and
fail-closed validation on every start and resume. Legacy tasks with
`confirmed_intent = NULL` retain their existing execution path; they are not
backfilled or reinterpreted. Historical checkpoints do not need new Skill
fields: confirmed-intent authority is derived from the current server-side
Task record, while legacy checkpoints continue through their existing path.
Existing TaskRun metadata, artifact authorization, old checkpoint formats and
NDVI recovery behavior remain readable and compatible. No migration is
required by this design; a changed persisted shape would need a separate
accepted migration decision.

## 3. Scientific and data contracts

These contracts are proposed and are not implementation-ready until the stated
evidence gates pass.

### Water / NDWI

`NDWI = (B03 - B08) / (B03 + B08)` using Sentinel-2 surface reflectance.
Water-class and change thresholds must be frozen and validated before 3B; an
index increase alone is not water-area evidence. Zero denominators, non-finite
values, nodata, clouds and shadows are invalid. Metrics include valid pixel
count/area, water area per period, water-area delta, and bounded mean indices;
zero valid pixels is a terminal verification failure.

### Urban / NDBI

`NDBI = (B11 - B08) / (B11 + B08)`. B11 must be deterministically resampled to
the target grid before calculation. An NDBI increase is an index change only;
it must not be labeled confirmed urban expansion without a validated
classification rule and evidence. Zero denominators and non-finite/masked
values are invalid. Metrics distinguish mean/index change from any thresholded
candidate built-up area.

### Shared raster and evidence rules

Each Skill must freeze target grid, CRS, resolution, alignment, resampling,
reflectance scaling/offset, SCL/cloud/shadow classes, nodata, valid-pixel
rules and pixel-area calculation. The current fixture proves only a 10 m,
EPSG:32650, aligned 64×64 B04/B08 window; it does not prove that future bands
share that grid.

The current manifest and STAC model expose no B03, B11 or SCL/cloud-shadow
assets. No asset identity or checksum is invented. Before 3B/3C, each period
needs a bounded fixture or approved evidence package containing item ID, date,
collection, AOI/window, CRS, dimensions, resolution, band and mask identities,
scale/offset/nodata, checksums, attribution and license metadata. Missing any
field blocks that batch.

## 4. Results, artifacts and UI

Results retain bounded shared fields: schema version, analysis type, mode,
summary, area/periods, data source, provenance summary, provenance, metrics,
artifact references and verifier status. Existing TaskRun metadata limits and
`stage_status` authority remain unchanged.

Existing `ndvi_before/after/change` remain unchanged. Proposed future names are
`ndwi_before/after/change` and `ndbi_before/after/change`; each must be
allowlisted per Skill and checked against the persisted result and tenant
authorization before serving. Streamlit shows type-specific metric labels and
captions while preserving evidence, provenance and technical views. Unknown or
unsupported historical types receive a bounded unsupported message and no
guessed rendering.

## 5. Batch gates

### 3A — Skill boundary + unchanged NDVI

Implement only the static mapping and NDVI adapter. Acceptance requires strict
type/indicator and plan validation; unchanged defaults, NULL behavior, old
checkpoint/TaskRun/artifact compatibility; fail-closed replan/resume tests;
focused intent/runtime/recovery/security tests; existing GeoChange,
conversation, Product UI and deterministic evaluation regression; applicable
PostgreSQL persistence tests; and Ruff, Pyrefly, format and diff checks.
The focused acceptance suite must also prove that:

- unknown and cross-Skill capabilities are rejected;
- invalid step order is rejected;
- replan cannot escape the selected Skill;
- resume cannot change Skill authority;
- malicious Planner output cannot override confirmed intent;
- capability output cannot override terminal or verifier facts; and
- legacy NULL-intent execution and old-checkpoint resume remain functional.

### 3B — First complete NDWI analysis

**BLOCKED** until B03/B08 plus mask evidence, checksums, grid contract and
validated thresholds are reviewed. Acceptance additionally requires
deterministic formula/mask/area tests, zero-denominator and zero-valid-pixel
negative tests, provenance binding, `ndwi_*` authorization, UI behavior,
recovery/tenant tests, PostgreSQL result persistence, affected regression and
static checks.

### 3C — NDBI analysis

**BLOCKED** until B11/B08 plus mask, resampling and provenance evidence is reviewed.
Acceptance additionally requires deterministic resampling/grid tests, explicit
separation of NDBI change from confirmed urban expansion, cross-Skill isolation,
artifact/UI/recovery/security tests, PostgreSQL persistence, affected
regression and static checks.

## 6. Status

Frozen/verified: reuse of the existing Runtime framework; server authority and
confirmed-intent boundary; nullable JSONB and 4096-byte limit; NDVI defaults;
NULL legacy behavior; existing TaskRun, checkpoint, artifact, stage-status and
UI evidence boundaries; and the current fixture facts.

ADR-014 is Accepted / frozen. Implementation 3A is READY FOR IMPLEMENTATION.
Implementation 3B and 3C remain BLOCKED pending B03/B11 and SCL/cloud-shadow
assets for both periods, checksums/provenance, grid/resampling rules, and
independent scientific validation.
