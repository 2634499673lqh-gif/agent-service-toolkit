## 3. Product and implementation boundary

Keep Streamlit. There is no evidence that forms, buttons, lists and explicit
refresh require React/Next.js. Add a Product view to `src/streamlit_app.py`,
defaulting to TaskPilot, before legacy user_id/history initialization. Retain
an explicitly labeled Legacy chat view and its existing behavior. Leaving
Product for Legacy clears Product credentials/data (attempt normal logout
first); never send a TaskPilot token to legacy endpoints or vice versa.

Use one small `src/taskpilot_ui.py` for Product rendering and one
`src/client/taskpilot.py` for a synchronous TaskPilotClient using existing httpx.
Do not subclass AgentClient or add a generic transport framework. Product
startup must not fetch `/info`, initialize legacy history, or require model
selection to log in. Existing AgentClient remains compatibility-only.
The client takes a server-configured base URL, never a UI-supplied endpoint;
no cross-origin redirects carrying credentials. Use finite 10-second request
timeouts, no automatic retries, and no `timeout=None` for Product requests.

Keep the client-only dependency group usable. Existing Task API schemas import
`persistence.models`/SQLAlchemy, absent from that group: do not import those
backend schemas into the client/UI. Narrow stdlib TypedDict wire views in the
client module may describe only consumed response fields; they are not a
second lifecycle model. No enum/domain refactor or dependency addition for UI.
FastAPI boundaries keep repository-native Pydantic request/response models.

The V1 exit is a **persisted-task management and evidence inspection UI**:
login, create, list/detail, create/inspect a run, discover existing runs,
inspect/decide existing approvals, inspect existing sanitized trace, logout.
An ordinary newly created run remains pending without an external trusted
internal runtime caller. No automatic execution, step completion, populated
trace, final-result generation, or approval resume is promised by this phase.
The UI labels that limitation next to start/status, not as a success animation.
If end-to-end public runtime execution becomes mandatory, stop and obtain a
separate accepted runtime-entry contract; do not silently wire an internal
service into Streamlit or change POST runs semantics.

Account setup remains the existing controlled bootstrap CLI after migrations.
After setup, these UI operations require neither Postman nor pasted bearer/run
IDs. Empty approvals/trace are valid. Populated acceptance scenarios use trusted
disposable test fixtures built with existing services (as in the PostgreSQL
API tests); no public seed API or production demo-data framework is added.

## 4. Authentication HTTP contract — explicit T118 backend work

Add `src/schema/auth_api.py`, `src/service/auth_api.py`; mount the router
directly on app, outside legacy verify_bearer. Reuse AuthService and
get_session_factory. No new table, migration, JWT, refresh token, cookie API,
public registration, password storage, or role hierarchy.

| Route | Input | Success/intermediate result | Failure |
|---|---|---|---|
| POST /api/v1/auth/login | JSON email string (1..320 chars), password string (1..1024 chars), optional organization_id UUID; extra fields forbidden | 200 `{access_token, token_type: "bearer", expires_at}` only after committed issuance; or 409 `{code: "ORGANIZATION_SELECTION_REQUIRED", organization_ids: [...]}` with only sorted/deduplicated eligible UUIDs and no session/token | 401 `{detail: "Not authenticated"}` with WWW-Authenticate: Bearer for unknown/wrong/inactive/malformed credentials, invalid selector, missing/extra/wrong-type fields or malformed body; no field input echo |
| GET /api/v1/auth/session | TaskPilot Authorization bearer | 200 `{user_id, membership_id, organization_id, role}` from fresh CurrentPrincipal | Existing generic 401 for missing/invalid/revoked/expired/inactive credential |
| POST /api/v1/auth/logout | TaskPilot Authorization bearer; no user/session/tenant selector | 204, current authenticated session revoked and committed; no body | Generic 401 when credential is already invalid, including repeated logout; fixed 503 on unavailable persistence |

All auth responses/errors use `Cache-Control: no-store`. Login returns fixed
503 `{detail: "Service unavailable"}` for persistence/service failure; never
return a token on failed/ambiguous commit. GET session uses the same fixed 503
on infrastructure failure. Local auth validation handling must not echo
password/input in FastAPI validation responses or logs; avoid a global change
to unrelated Task/legacy validation semantics. Catch operational failures at
the auth boundary with safe logging, so raw driver exceptions/parameters do
not reach the existing request middleware's exception logging. No passwords,
tokens, token digests, headers or request/response bodies in logs/test artifacts.

Existing AuthService.login/revoke APIs flush under caller-owned transactions;
preserve their signatures/behavior for internal callers. Add minimal
commit-owning HTTP orchestration methods in `src/service/session.py` that call
them, commit before returning a successful credential/revocation, and roll back
failures. Routes map typed results, not identity or authorization policy.
Session dependency owns close; service owns commit/rollback, repositories do
not commit. Logout derives its target only from the authenticated principal
and matching stored session; it cannot revoke arbitrary submitted IDs.
Selection-required issues no credential and writes no AuthSession.

UI login submits password once and clears the password widget immediately
after every attempt, including failure/selection. For multiple organizations,
show only returned IDs and ask for password again with explicit selection;
fresh login rechecks password and eligibility, not a cached chooser credential.
No default-first/owner-first selection. Switching organization means logout
and fresh login; existing sessions are never rebound.

The raw bearer is held only in the individual Streamlit server-side session's
client object as necessary transient transport material, with a non-secret
repr. No cache_resource/cache_data, shared singleton, disk, query string,
browser storage, download, tracing or checkpoint contains it. This credential
is not UI identity authority: every HTTP request still resolves CurrentPrincipal.
GET session supplies display identity/role only; refresh it on Product reruns.
Transient identity display and fetched data are discarded on logout/401/account
change, together with task/run/approval navigation and form remnants. Browser
reconnect may require login again; no persistent remember-me session.

Logout attempts remote revocation once and always clears local credentials.
If timeout/503 prevents confirmation, state "Local session cleared; server
sign-out could not be confirmed"; do not claim revocation. The existing 24-hour
server expiry remains the fallback, without retaining the token for retries.
HTTPS is required outside local loopback for browser/UI and UI/API links;
this is a transport precondition, not deployment work or an internet-readiness
claim. General rate limiting/backpressure stays T123.

## 5. Task/run contract and explicit T119 backend work

- Create accepts exactly title and optional description. Title must be nonblank
  and 1..255 characters. Objective/criteria may be prose in description, not new
  structured fields. Never submit user/organization/role/status from UI.
- List shows the current tenant's server-returned tasks (not only creator's
  tasks); detail re-fetches by ID. No direct SQL, thread-history fallback or
  persistent cross-session data cache. Render task text as text, not unsafe HTML.
- Update/cancel UI is excluded: not necessary for this narrow exit; existing
  PATCH/cancel API and its unusual owner/admin/member policy remain untouched.
- Add only GET `/api/v1/tasks/{task_id}/runs` returning 200
  `list[TaskRunResponse]`, ordered `(run_number ASC, id ASC)`. Valid visible
  task with no runs returns `[]`; absent/foreign task returns identical 404;
  unauthenticated returns generic 401. All active tenant roles can read it.
  Resolve visible parent first and reuse `list_for_task_in_organization` with
  principal.organization_id; no tenant query/body selector. It is read-only,
  with no change to start/inspect/lifecycle semantics or repository commits.
  Like current Task list, V1 returns the full list: no invented page token,
  latest-run pointer, new index, pagination framework or scalability claim.
- Start is explicit form/button submission only. DRAFT or FAILED can start;
  show FAILED's action as retry/new attempt. Other states have no enabled start
  action, but the server remains final authority (409 on races). All active
  in-tenant roles can start under the current API; do not reuse management or
  approval roles as a new start restriction. No Idempotency-Key contract exists.
- On success re-read Task, run list and selected run. On timeout or lost response,
  do not retry POST automatically: show unknown outcome and refresh those reads
  before permitting a new deliberate action. Repeated clicks/reruns must not
  replay mutations. For lost create response, refresh task list for inspection;
  do not guess identity by matching a non-unique title or claim deduplication.
- Run details contain only id, task_id, run_number, status, created_at and
  updated_at. Do not turn updated_at into a transition history or finished_at.
  No TaskStep, progress percentage, plan download, runtime-state endpoint,
  internal WAITING_APPROVAL TaskRun enum, resume button or result endpoint.

## 6. Approvals and trace

T114's "queue" is labeled **Approvals for selected run**; users navigate
Task list → Task → run list → approvals. No global scan/fan-out across tasks.
Read list then detail through exact nested IDs. Show immutable action/version,
full API-sanitized proposal, L2 risk, status, requester/decider and timestamps,
reason and zero-based replan/step coordinates. Do not expose internal
action_state/outcome, which ApprovalResponse does not return.

Only current owner/admin display approve/reject for PENDING; member is read-only.
Display role is a hint, never permission proof. Detail and Task/Run are re-read
before a deliberate decision; terminal/stale states disable action. Submit
only optional reason (at most 500 chars); require an explicit decision on the
displayed proposal, with no automatic approve, proposal edits or actor fields.
Server enforces active run, role, tenant and immutable first decision; duplicate
or competing decisions are 409, including identical decisions. After decision,
refresh detail/list and Task/Run; on timeout/409 refresh rather than retry.
An APPROVED decision does not mean executed/resumed. L3 is blocked and creates
no approvable row; never fabricate an L3 approval or execution control.

T115 consumes only GET trace with `limit=100` by default and explicit choices
100/500. Preserve response order, which the server defines as
`started_at ASC, event_kind_rank ASC, agent_run_id ASC, call_index ASC NULLS
FIRST, event_id ASC`; agent events precede tool events at a timestamp tie.
No client sort/group may reorder this sequence. Use event_id as row identity;
show kind/node/tool, status, UTC timestamps, duration, zero-based step/replan/
retry coordinates and approved correlation fields. Null usage/estimate/duration
is unavailable/not observed, never zero. Cost is an estimate, never billing.
If response count equals limit, say the bounded view may be incomplete; at 500
do not promise pagination or complete history. Empty means no observed events,
not a failed or unstarted run inferred from telemetry.

Allow only TraceEventResponse fields; no ToolCall arguments/result, prompts,
raw responses, stack traces, credentials, checkpoint content or extra payloads.
Render sanitized textual content without executing HTML/URLs/markup. An
approval_id can navigate only to the same run's protected approval detail.
Always fetch current Approval/TaskRun there; observation `waiting_approval`,
usage, result hints and IDs cannot grant authority or mutate lifecycle.

## 7. State ownership and bounded error/loading UX

Backend is the sole business authority. Session state contains navigation IDs,
unsent forms, UI preferences and the transient credential described in section 4;
fetched snapshots are display-only and are replaced by reads, never mutated
locally into authoritative lifecycle/approval truth. No persisted task/run/
approval cache or state machine; no optimistic success. Changing task clears
run/approval selection, changing run clears approval selection, and logout/401
clears all Product state. Every protected render refreshes its selected resource;
explicit refresh re-reads current server truth. No websocket, timer/background
poller or unbounded refresh loop. Disable mutation controls while in flight.

| Condition | UI behavior |
|---|---|
| Loading | Spinner near requested view; at most one request per explicit operation/read; finite timeout; no implied progress percentage |
| 401 | Clear credential and all protected snapshots/navigation, show generic sign-in prompt; never fall back to AUTH_SECRET |
| 403 | Fixed permission-denied text; do not retry or expose backend details; refresh display identity if needed |
| 404 | Same unavailable-resource message for missing/foreign/wrong nesting; clear selected descendant and return to parent list |
| 409 | Normal resource mutation: stale/conflicting state message and fresh reads; login selection is the typed special case in section 4 |
| 422 | Safe field-level guidance from known local constraints, otherwise generic invalid input; never dump response/input |
| Timeout/network/5xx/malformed response | Fixed service-unavailable message; manual retry for reads; mutation outcome unknown and reconcile by reads; no exception/body/URL/header rendering |
| Empty | Separate no tasks, no runs, no approvals for this run, no trace evidence; no fabricated success/failure |

The client exposes bounded error classification/status and a validated optional
X-Request-ID UUID, never raw response/exception text. No sensitive backend
detail in messages, error objects, repr or test snapshots. Baseline handling
ships with each flow; T116 integrates and tests it, not postpones auth safety.

## 8. Deferred scope and risk boundaries

Exclude React/Next.js rewrite, generic design system, websockets/live background
updates, TaskStep persistence, public runtime execute/resume API, worker/queue
UI, knowledge/file upload, Evaluation dashboard, admin console, organization
management, task update/cancel UI, feedback integration, deployment work,
public registration/SSO/refresh-token/remember-me systems, external effects and
L3 execution. No schema/migration/dependency/CI change is needed for this plan.
Do not reuse legacy RAG/file/voice features as tenant-safe Product capabilities.

Key risks and required mitigation: credential cross-session leakage (session-only
client and isolation tests); validation/driver secret echo (auth negative tests);
stale tenant/role (fresh server principal and state clearing); duplicate write
after timeout (no automatic retry); misleading runtime/trace authority (honest
labels, separate read contracts); legacy regressions (retain/test Legacy view);
client-only imports (import smoke with existing client dependencies).

## 10. Required implementation evidence and review rules

These are future implementation requirements, not tests run by Planning.
Task Cards supply scoped files and focused commands. Use real disposable
PostgreSQL for HTTP auth issuance/revocation/rollback and tenant run discovery;
mock-only or skipped PostgreSQL tests are insufficient at Batch A/T117.
Keep tests deterministic and provider-free. AppTest and httpx mocks cover
two simultaneous sessions, account switches, all errors, reruns and unknown
mutation outcomes; fixture-backed HTTP integration covers the full credential
to protected API chain and populated approval/trace scenarios. Browser smoke
must confirm readable forms, full proposal visibility and no raw errors.

At backend authentication gate and Final Audit run full `uv run pytest` with
`TASKPILOT_TEST_DATABASE_URL` pointing only to a disposable migrated PostgreSQL
database; report database skips as missing evidence. Run affected Task/Approval/
trace/runtime security regression, `uv run ruff check --output-format concise`,
`uv run ruff format --check .`, `uv run pyrefly check`, `uv lock --check`, and
`git diff --check` as applicable. Existing pyrefly excludes streamlit_app;
do not claim it type-checks the excluded entrypoint. New Product/client modules
must be covered. Client-only smoke must prove no SQLAlchemy/service/voice import
is needed to import the thin Product client/module; do not change dependencies
or lock merely to run this check.

Final Audit verifies the whole accepted ADR and the UI acceptance boundary,
current docs, existing lifecycle/concurrency/approval/redaction regressions,
negative cases, shared-suite/static evidence and deferred-scope compliance.
No migration rerun is required just for adding routes if persistence is unchanged;
existing integration fixtures must still use the real migrated schema.
Substantive Strong Review and Final Audit are independent and read-only;
blockers return to implementation, with no reviewer fix. Verdict is exactly
APPROVED or NOT APPROVED. Only after independently determining APPROVED may
the reviewer mechanically synchronize explicit stale status lines under AGENTS.
No commit/push is performed by Planning or implicitly authorized for later work.
