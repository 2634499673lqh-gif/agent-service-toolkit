# ADR-012 — Phase 10 concurrency and deployment hardening

Date: 2026-09-26  
Status: Accepted / frozen; Phase 10 Planning Strong Review APPROVED.

T120 is COMPLETE / APPROVED. Implementation begins with T121, T123, and T124.

## Context and verified baseline

Phase 9 is merged at `a4786ad` and this branch is `phase-10-concurrency-deployment-hardening`.
Business data uses PostgreSQL-only SQLAlchemy async sessions. `TaskLifecycleService` locks the
tenant-scoped Task and commits each transition; PostgreSQL enforces one active run and unique run
numbers. Approval uses Task → TaskRun → Approval row locks and unique action identity. Runtime
validation and terminal completion use discrete transactions; no business transaction is held
across graph/checkpoint work. Existing PostgreSQL tests already cover concurrent task start,
approval decisions, approved-action delivery, cancellation races, and concurrent runtime resume.
The Product UI uses bounded 10-second requests and no automatic mutation retry.

The current gaps are operational: the business engine has only `pool_pre_ping` and implicit pool
defaults; the LangGraph saver/store each create separate pools from `POSTGRES_MIN/MAX...`;
there is no explicit pool timeout or lifecycle disposal contract; `/health` is process-only and
may perform an external Langfuse check; Compose checks the protected `/info`; CI has no required
PostgreSQL service/concurrency tier; and the service/app images do not copy every Phase 9 module.

## Decisions

1. **Concurrency authority.** Keep PostgreSQL row locks, unique constraints, and service-owned
   short transactions as the authority. Add exact TaskRun identity checks to terminal runtime
   transitions and fresh reads after contested operations. Do not add distributed locks, leases,
   exactly-once claims, or a generic queue. Duplicate graph work remains an explicitly bounded
   limitation; only one durable lifecycle/effect winner is required.
2. **Transaction boundary.** No transaction may span model/provider, graph, checkpoint, UI, or
   external network work. Runtime phases are: validate/read, commit begin, execute outside the
   business transaction, then lock/revalidate/persist terminal evidence and commit. Approval and
   cancellation preserve the existing lock order.
3. **Pools and ownership.** Add typed settings for business SQLAlchemy pool size/overflow,
   checkout timeout, and recycle with conservative local defaults; configure `pool_pre_ping`.
   Configure LangGraph pool bounds from the existing settings and give each pool an explicit
   application name. The process lifespan owns disposal of the business engine/factory and
   saver/store contexts. Pool exhaustion is a bounded 503/backpressure signal, never an unbounded
   wait or retry loop. Do not claim one global pool: business and LangGraph persistence remain
   separate pools.
4. **Worker.** No background worker is required for the Phase 10 exit. The public UI does not
   execute runtime, and the internal runtime is an explicit trusted call. T122 is deferred until
   a durable queue/lease/recovery contract and an accepted runtime entry point exist.
5. **Backpressure.** Apply a small in-process semaphore/limit at the API/runtime boundary to
   bound expensive LLM/graph work and return a fixed 429/503 when saturated. It is per process,
   observable, and not a distributed rate limiter. Read-only health/auth and cheap CRUD are not
   blocked by the runtime limit. Configuration and reset-on-shutdown belong to the service.
6. **Health semantics.** `/health/live` is liveness: process/event loop responds and performs no
   dependency query. `/health/ready` is readiness: service startup completed and a bounded
   PostgreSQL `SELECT 1` succeeds; LangGraph checkpoint/store readiness is included only when
   configured for PostgreSQL. Langfuse/LLM providers are not readiness dependencies. Existing
   `/health` remains a compatibility alias with the liveness shape until implementation proves
   otherwise; Compose uses readiness.
7. **Compose.** Pin image major versions already supported, use health-gated `depends_on`,
   named volume, explicit non-secret defaults only for local demo, bounded stop grace, restart
   policy, and a one-shot migration/init path before API readiness. Do not publish PostgreSQL
   outside the developer default unless explicitly opted in. Health checks must use unauthenticated
   health routes. No Redis, worker, Kubernetes, or production internet hardening is added.
8. **CI evidence.** Every change runs lock check, lint/format, type check, unit/evaluation tests,
   and the existing Docker build/config smoke. A PostgreSQL-backed integration/concurrency job is
   required for Phase 10 acceptance (disposable service, migrations, focused race tests); heavier
   Compose end-to-end remains an explicit Docker job, not a silently skipped required check.
9. **Multi-user smoke.** Prove two independent authenticated sessions in one organization and
   one foreign organization concurrently create/list/start tasks, race one start and one approval,
   and verify tenant isolation, one active run, immutable approval decision, and no stale UI data.
   This is a deterministic two-user smoke, not a load-testing platform.

## Deferred scope and acceptance boundary

Deferred: worker/queue/lease, Redis or distributed rate limits, websocket execution, autoscaling,
Kubernetes, external observability, backups/failover, real external effects, exactly-once provider
semantics, load testing, and generic production-readiness claims. Acceptance requires real
PostgreSQL race evidence, pool exhaustion/timeout behavior, liveness/readiness dependency matrix,
Compose migration/startup/restart evidence, CI artifacts, and the deterministic two-user smoke.
