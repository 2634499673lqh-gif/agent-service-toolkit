# ADR-008 — Phase 6 human approval and safety boundary

Date: 2026-09-22
Status: proposed (Phase 6 Planning Strong Review required)

## Context

Phase 5 provides a deterministic, read-only, in-process capability path. Phase 6
must introduce the smallest safe boundary for a future side effect without
turning TaskPilot into a policy or workflow platform.

## Decisions

1. Risk is classified server-side from the selected capability/action metadata
   and validated arguments immediately before dispatch. L0 is read-only and
   auto-allowed; L1 is reversible internal work and is policy-allowed; L2
   requires an approval record; L3 is blocked in V1. Model output, checkpoint
   data, caller fields, and retrieved content cannot classify authority.
2. One tenant-scoped Approval record is the business source of truth. It stores
   task/run identity, immutable sanitized proposed action, risk level, status,
   requester, decision actor/reason, timestamps, and a deterministic action key.
   It does not store secrets or raw credentials. LangGraph checkpoints remain
   separate persistence.
3. Approval decisions require an active owner or admin membership in the task
   organization. Cross-tenant reads and decisions are indistinguishable from
   missing resources (404); in-tenant insufficient role is 403. A decision is
   terminal and cannot be changed. The proposed action is never accepted from
   an approve/reject request.
4. Approval is a runtime boundary, not a new general lifecycle enum. The
   TaskRun remains RUNNING while the checkpoint records a validated pending
   approval; the runtime result reports WAITING_APPROVAL. Cancellation and
   terminal business state win over a stale approval. A resume revalidates
   tenant, run, approval, and checkpoint identity in one service transaction
   before the effect boundary.
5. Phase 6 includes one deterministic mock side effect only. Its action key is
   enforced by a database uniqueness constraint and an atomic claim/record
   operation so duplicate HTTP or worker delivery cannot execute twice. No
   exactly-once claim is made for an uncooperative external provider.
6. Rejection, L3 classification, malformed approval data, missing checkpoint,
   stale decision, authorization failure, and ambiguous effect ownership fail
   closed. Approval payloads and logs are sanitized; secrets, credentials,
   ORM/session objects, and authority never enter AgentState or checkpoints.

## B1 — Approval persistence contract (T081)

One new table, `taskpilot.approvals`; no effect, policy, or workflow table.
Required columns (NOT NULL unless explicitly nullable):

| Columns | Contract |
|---|---|
| `id` | Application-generated UUID4 primary key |
| `task_run_id` | UUID FK to `taskpilot.task_runs.id`, ON DELETE RESTRICT |
| `replan_count`, `step_position` | Integers, respectively 0..1 and >= 0 |
| `action_name`, `action_version` | Non-empty strings, at most 128 / 64 characters; trusted fixed mock-action identity |
| `proposed_action` | JSONB object, at most 8192 UTF-8 bytes in canonical JSON; complete bounded sanitized arguments, not a lossy preview |
| `risk_level` | String constrained to L2; other levels create no approval |
| `requester_membership_id` | UUID FK to `taskpilot.memberships.id`, ON DELETE RESTRICT |
| `status` | PENDING, APPROVED, REJECTED; default PENDING |
| `decider_membership_id`, `decided_at`, `decision_reason` | Nullable membership FK (RESTRICT), timestamptz, and string <= 500 characters |
| `created_at`, `updated_at` | UTC timestamptz, service-managed |
| `action_state` | AVAILABLE, COMPLETED, FAILED; default AVAILABLE |
| `outcome`, `action_finished_at` | Nullable JSONB bounded ExecutionResult, nullable UTC timestamptz |

Ownership is normalized: `Approval.task_run_id -> TaskRun.task_id ->
Task.organization_id`. No duplicate task/organization columns that can disagree.
Every approval lookup/list/update joins both TaskRun and Task with
`Task.organization_id = server_principal.organization_id`; nested task/run IDs
are also SQL predicates, not post-fetch comparisons. Existing TaskRun/Task
RESTRICT foreign keys complete the ownership chain. Requester/decider are
server-derived active memberships in that same organization, checked by the
service; membership FKs retain actor evidence and membership identifies user.

UNIQUE `(task_run_id, replan_count, step_position)` is both the approval identity
constraint and action-key uniqueness constraint. Index `(task_run_id, status)`
supports scoped queries. Named CHECKs enforce the ranges/enums, string bounds,
JSON object types, and these combinations: PENDING has no decision fields;
APPROVED/REJECTED require decider and decided_at (reason optional); AVAILABLE
has no outcome/finished time; COMPLETED/FAILED require APPROVED plus outcome
and finished time. COMPLETED contains a valid successful ExecutionResult;
FAILED contains a valid sanitized failed ExecutionResult. The service validates
full JSON schemas/byte bounds before flush. No public proposal/identity edit or
delete operation; repositories expose no such mutation. Decision and action
transitions are conditional and terminal values immutable.

Repositories query/add/flush only. Services own commit/rollback on the supplied
session; no repository commits or replaces it. Mutating transactions lock the
tenant-scoped Task first, then its TaskRun, then Approval, using fresh database
values (refresh existing identity-map objects). This follows T035's parent lock
and serializes against cancellation/terminal completion. Lifecycle changes
remain exclusively T035 operations outside approval transaction commits.

## B2 — Canonical request identity and create/reuse (T082/T083)

The canonical key is `(task_run_id, replan_count, step_position)`: one L2 action
per PlanStep in the fixed Phase 6 mock path. Retry does not change the key;
accepted replan uses the existing monotonic replan_count, never a new budget.
No nonce, checkpoint ID, client idempotency header, or payload hash creates a
second approval for the same slot. Name, version and full validated canonical
arguments are immutable proposal data, compared on every reuse. Canonical JSON
uses sorted object keys, compact separators, UTF-8, and no NaN/Infinity; it is
computed only after the fixed action's typed argument validation. A mismatch is
a conflict, never an update or a second request. A different key supplied only
by a caller/checkpoint cannot grant approval: trusted dispatch must validate
the run/plan slot and the database proposal before any effect.

Create-or-reuse is one service-owned business transaction with the B1 lock
order. Require current Task/TaskRun RUNNING and the requested active run; insert
PENDING if the key is absent, otherwise return the identical existing record
without resetting decision, actor, outcome, or timestamps. Concurrent creators
serialize on Task; after waiting they re-read and reuse. The unique constraint
is the final guard: an unexpected uniqueness violation rolls back and returns
a conflict, with no implicit retry loop. A committed approval followed by a
failed checkpoint write is safe: no effect occurred and a replay reuses it.
Checkpoint persistence is a later independent operation; return waiting only
after its success. Missing/corrupt checkpoints fail closed under existing rules.

Approve/reject locks in the same order, validates tenant and current owner/admin
authority, and accepts only PENDING on a still-RUNNING active run. First commit
wins; every repeated or competing decision returns conflict (HTTP 409), even
when identical. No proposal or authority fields are accepted in decision input.
Repeated create returns existing REJECTED/APPROVED evidence, never reopens it.
Cancellation or a terminal run makes create/decision/resume conflict; stale
records remain readable for audit but cannot authorize work. Rejection has no
effect and runtime resolves it through T035 fail_run, preserving any terminal
winner. Decision and lifecycle are not represented as one cross-store commit.

## B3 — Atomic mock action claim/outcome (T084)

The approved-action service owns one short PostgreSQL transaction. It locks
Task -> TaskRun -> Approval, rechecks active RUNNING business state, persisted
APPROVED decision and exact proposal/key, then handles action_state. The action
key is exactly B2's tuple; there is no independent caller-selected key.

- AVAILABLE: eligible only after the checks above; the row lock is the claim.
- In progress: transaction-local ownership of that lock, not a durable state.
  Use NOWAIT acquisition for this action path; contention at any lock returns
  a bounded busy/conflict result without invoking the mock or retrying inside
  the service. After rollback, a later explicit call can inspect durable state.
- COMPLETED: return the stored outcome without invoking the action again.
- FAILED: return the stored sanitized failure; never reacquire or rerun it.

Only AVAILABLE/COMPLETED/FAILED are durable. The mock's sole observable effect
is recording its bounded outcome on this Approval row; any calculation before
that write is deterministic and side-effect-free. It performs no network,
filesystem, callback, or independent-transaction mutation. Outcome plus
COMPLETED (or a caught deterministic failure plus FAILED) commit atomically
before releasing the claim. Crash/DB failure rolls back both: AVAILABLE remains
and a later explicit call may recalculate, but no committed mock effect is
duplicated. Unknown commit outcome is resolved by reading business persistence
on the next call, never by blindly re-executing. No durable CLAIMED state,
lease, lock token, reaper, or claim recovery workflow is needed.

Cancellation uses the same Task lock. If cancellation wins first, no claim or
effect occurs; if effect commits first, its audit outcome remains and a later
cancellation may win the T035 terminal transition. No completion overwrites
that terminal state. A cancelled/terminal run cannot resume even if COMPLETED;
read-only inspection may still expose the stored outcome. A crash after effect
commit but before checkpoint update replays from business COMPLETED, not the
mock action. Checkpoint approval/result fields never substitute for these
checks. FAILED is terminal for this mock action, not RETRY/REPLAN eligible;
existing read-only capability retry/replan budgets remain unchanged.

Required evidence (future implementation, not planning tests): independent
PostgreSQL sessions for concurrent create/reuse, approve-vs-reject, duplicate
claim/busy/completed, cancellation before/after effect, stale identity-map reads,
rollback before commit and replay after commit/before checkpoint; verify one
committed mock outcome, SQL tenant predicates, FK/check/unique violations,
immutable proposals, actor authorization and redaction. Migration up/down must
preserve existing TaskPilot and LangGraph tables. Worker delivery is simulated
by duplicate internal calls, not a new worker implementation.

## Consequences and deferrals

A new approval table and migration are required. Existing Task/TaskRun enums,
T035 lifecycle ownership, retry/replan budgets, checkpoint identity, and
Phase 5 deterministic context contracts remain unchanged. Generic policy/rule
DSLs, workflow engines, distributed locks, workers, credentials, real external
effects, and UI are deferred.

## Acceptance

T080–T084 are implementation-ready only if an independent Planning Strong Review
accepts this ADR and the task DAG. T085 is the read-only Phase 6 Final Audit.
