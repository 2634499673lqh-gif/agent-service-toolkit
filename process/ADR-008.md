# ADR-008 — Phase 6 human approval and safety boundary

Date: 2026-09-22
Status: Accepted. T080 Focused Strong Re-review approved ADR-008 on 2026-09-23; the contract is frozen.

## Context

Phase 5 provides a deterministic, read-only, in-process capability path. Phase 6
must introduce the smallest safe boundary for a future side effect without
turning TaskPilot into a policy or workflow platform.

## Decisions

1. One pure, deterministic server-side classifier runs after the fixed
   capability/action has been selected by trusted server wiring and its typed
   arguments have been validated, immediately before dispatch. Its inputs are
   only that trusted action metadata and the validated argument object; it
   never accepts a risk level or action identity from the caller, model,
   PlanStep text, checkpoint, or retrieved content. L0 is read-only and
   automatically allowed; L1 is reversible internal work and automatically
   allowed; L2 requires an approval record; L3 is blocked in V1. An unknown or
   mismatched action/version, invalid arguments or metadata, absent result, or
   classifier error fails closed before dispatch: no approval is created and
   no action runs. Phase 6 implements only its one fixed deterministic L2 mock
   action; this does not create a configurable registry, policy engine, or DSL.
2. One tenant-scoped Approval record is the business source of truth. It stores
   task/run identity, immutable sanitized proposed action, risk level, status,
   requester, decision actor/reason, timestamps, and a deterministic action key.
   It does not store secrets or raw credentials. LangGraph checkpoints remain
   separate persistence.
3. Approval decisions require an active owner or admin membership in the task
   organization. Cross-tenant reads and decisions are indistinguishable from
   missing resources (404); in-tenant insufficient role is 403. A decision is
   terminal and cannot be changed. The proposed action is never accepted from
   an approve/reject request.
4. Approval is a runtime boundary, not a Task or TaskRun lifecycle state; the
   existing `TaskStatus` and `TaskRunStatus` enums remain unchanged. The
   TaskRun remains RUNNING while the checkpoint records only a validated
   pending-approval reference: canonical `approval_id`, `replan_count`, and
   zero-based `step_position` (the current `AgentState.plan_position`). The
   reference has no status, proposal, decision, or authority fields and is
   only a lookup hint. The runtime result reports `WAITING_APPROVAL` and the
   approval ID only; it does not copy the proposal or decision. It is returned
   only after the independent checkpoint write succeeds. A resume treats the
   checkpoint as untrusted, revalidates tenant, task/run/checkpoint identity,
   approval identity and current action proposal against business persistence
   under the service transaction before the effect boundary. Cancellation and
   terminal business state win over a stale approval.
5. Phase 6 includes one deterministic mock side effect only. Its action key is
   enforced by a database uniqueness constraint and an atomic claim/record
   operation so duplicate HTTP or worker delivery cannot execute twice. No
   exactly-once claim is made for an uncooperative external provider.
6. Rejection, L3 classification, malformed approval data, missing/corrupt
   checkpoint, stale decision, authorization failure, unknown classifier
   input/result, and ambiguous effect ownership fail closed: no effect is
   invoked. Runtime-recoverable terminal failures are resolved through T035;
   an already-won terminal state is preserved. Approval payloads and logs are
   sanitized; secrets, credentials, ORM/session objects, decision status, and
   authority never enter AgentState or checkpoints. The bounded pending-
   approval reference above is identity only, never proof of approval.

## B1 — Approval persistence contract (T081)

One new table, `taskpilot.approvals`; no effect, policy, or workflow table.
Required columns (NOT NULL unless explicitly nullable):

| Columns | Contract |
|---|---|
| `id` | Application-generated UUID4 primary key |
| `task_run_id` | UUID FK to `taskpilot.task_runs.id`, ON DELETE RESTRICT |
| `replan_count`, `step_position` | Integers, respectively 0..1 and >= 0. `step_position` is the zero-based plan slot (`AgentState.plan_position`); the corresponding `PlanStep.position` and `ExecutionResult.step_position` are one-based and equal `step_position + 1`. |
| `action_name`, `action_version` | Non-empty strings, at most 128 / 64 characters; trusted fixed mock-action identity |
| `proposed_action` | JSONB object, at most 8192 UTF-8 bytes in canonical JSON; complete bounded sanitized arguments, not a lossy preview |
| `risk_level` | String constrained to L2; other levels create no approval |
| `requester_membership_id` | UUID FK to `taskpilot.memberships.id`, ON DELETE RESTRICT |
| `status` | PENDING, APPROVED, REJECTED; default PENDING |
| `decider_membership_id`, `decided_at`, `decision_reason` | Nullable membership FK (RESTRICT), timestamptz, and string <= 500 characters |
| `created_at`, `updated_at` | UTC timestamptz, service-managed |
| `action_state` | AVAILABLE, COMPLETED, FAILED; default AVAILABLE |
| `outcome`, `action_finished_at` | Nullable JSONB ExecutionResult object, at most 8,192 UTF-8 bytes after canonical JSON serialization; nullable UTC timestamptz |

Ownership is normalized: `Approval.task_run_id -> TaskRun.task_id ->
Task.organization_id`. No duplicate task/organization columns that can disagree.
Every approval lookup/list/update joins both TaskRun and Task with
`Task.organization_id = server_principal.organization_id`; nested task/run IDs
are also SQL predicates, not post-fetch comparisons. Existing TaskRun/Task
RESTRICT foreign keys complete the ownership chain. Requester/decider are
server-derived active memberships in that same organization, checked by the
service; membership FKs retain actor evidence and membership identifies user.

UNIQUE `(task_run_id, replan_count, step_position)` is both the approval identity
constraint and action-key uniqueness constraint. Index `(task_run_id, status)`
supports scoped queries. Named CHECKs enforce the ranges/enums, string bounds,
JSON object types, and these combinations: PENDING has no decision fields;
APPROVED/REJECTED require decider and decided_at (reason optional); AVAILABLE
has no outcome/finished time; COMPLETED/FAILED require APPROVED plus outcome
and finished time. COMPLETED contains a valid successful ExecutionResult;
FAILED contains a valid sanitized failed ExecutionResult. The service validates
the full existing `ExecutionResult` schema (including its 2,000-character
output, 64-character error-code, and 500-character sanitized-message bounds),
requires the result's one-based step position to equal
`Approval.step_position + 1`, and enforces the 8,192-byte canonical JSON bound
before flush. Canonical JSON uses sorted keys, compact separators, UTF-8, and
rejects NaN/Infinity. No public proposal/identity edit or delete operation;
repositories expose no such mutation. Decision and action transitions are
conditional and terminal values immutable.

Repositories query/add/flush only. Services own commit/rollback on the supplied
session; no repository commits or replaces it. Mutating transactions lock the
tenant-scoped Task first, then its TaskRun, then Approval, using fresh database
values (refresh existing identity-map objects). This follows T035's parent lock
and serializes against cancellation/terminal completion. Lifecycle changes
remain exclusively T035 operations outside approval transaction commits.

## B2 — Canonical request identity and create/reuse (T082/T083)

The canonical key is `(task_run_id, replan_count, step_position)`: one L2 action
per zero-based plan slot in the fixed Phase 6 mock path. `task_run_id` is
resolved from the tenant-scoped active run; `replan_count` is the existing
bounded runtime counter (0..1); `step_position` is the current zero-based
`AgentState.plan_position`, checked against the validated plan and current
`PlanStep`. Retry does not change the key; an accepted replan advances the
existing monotonic `replan_count` and uses the existing replan budget. The
corresponding `PlanStep.position` is one-based and must equal
`step_position + 1`. No nonce, checkpoint ID, client idempotency header, or
payload hash creates a second approval for the same slot. Name, version and
full validated canonical arguments are immutable proposal data, compared on
every reuse. Canonical JSON uses sorted keys, compact separators, UTF-8, and no
NaN/Infinity; it is computed only after the fixed action's typed argument
validation. A mismatch is a conflict, never an update or a second request. A
different key supplied only by a caller/checkpoint cannot grant approval:
trusted dispatch must validate the run/plan slot and the database proposal
before any effect.

The checkpoint's pending-approval reference contains exactly the canonical
`approval_id`, `replan_count`, and zero-based `step_position` described above;
`task_run_id` remains the existing AgentState identity. Extra fields are
rejected. Resume compares all of these values to the tenant-scoped active run,
the Approval row, the currently validated plan slot, and the freshly validated
action name/version/arguments. The checkpoint reference cannot supply or
replace any proposal or decision data.

Create-or-reuse is one service-owned business transaction with the B1 lock
order. Require current Task/TaskRun RUNNING and the requested active run; insert
PENDING if the key is absent, otherwise return the identical existing record
without resetting decision, actor, outcome, or timestamps. Concurrent creators
serialize on Task; after waiting they re-read and reuse. The unique constraint
is the final guard: an unexpected uniqueness violation rolls back and returns
a conflict, with no implicit retry loop. A committed approval followed by a
failed checkpoint write is safe: no effect occurred and a replay reuses it.
Checkpoint persistence is a later independent operation; return waiting only
after its success. Missing/corrupt checkpoints fail closed under existing rules.

Approve/reject locks in the same order, validates tenant and current owner/admin
authority, and accepts only PENDING on a still-RUNNING active run. First commit
wins; every repeated or competing decision returns conflict (HTTP 409), even
when identical. No proposal or authority fields are accepted in decision input.
Repeated create returns existing REJECTED/APPROVED evidence, never reopens it.
Cancellation or a terminal run makes create/decision/resume conflict; stale
records remain readable for audit but cannot authorize work. Rejection has no
effect and runtime resolves it through T035 fail_run, preserving any terminal
winner. Decision and lifecycle are not represented as one cross-store commit.

## B3 — Atomic mock action claim/outcome (T084)

The approved-action service owns one short PostgreSQL transaction. It locks
Task -> TaskRun -> Approval, rechecks active RUNNING business state, persisted
APPROVED decision and exact proposal/key, then handles action_state. The action
key is exactly B2's tuple; there is no independent caller-selected key.

- AVAILABLE: eligible only after the checks above; the row lock is the claim.
- In progress: transaction-local ownership of that lock, not a durable state.
  Use NOWAIT acquisition for this action path; contention at any lock returns
  a bounded busy/conflict result without invoking the mock or retrying inside
  the service. After rollback, a later explicit call can inspect durable state.
- COMPLETED: return the stored outcome without invoking the action again.
- FAILED: return the stored sanitized failure; never reacquire or rerun it.

Only AVAILABLE/COMPLETED/FAILED are durable. The mock's sole observable effect
is recording its bounded `ExecutionResult` on this Approval row; any
calculation before that write is deterministic and side-effect-free. The result
uses the existing schema: successful output is at most 2,000 characters;
failure has no output, a non-empty error code of at most 64 characters, and an
optional sanitized message of at most 500 characters. Its step position must
match the one-based PlanStep slot. Canonical serialized outcome is at most
8,192 UTF-8 bytes. The mock performs no network, filesystem, callback, or
independent-transaction mutation. Outcome plus COMPLETED (or a caught
deterministic failure plus FAILED) commit atomically before releasing the
claim. Crash/DB failure rolls back both: AVAILABLE remains and a later explicit
call may recalculate, but no committed mock effect is duplicated. Unknown
commit outcome is resolved by reading business persistence on the next call,
never by blindly re-executing. No durable CLAIMED state, lease, lock token,
reaper, or claim recovery workflow is needed.

Cancellation uses the same Task lock. If cancellation wins first, no claim or
effect occurs; if effect commits first, its audit outcome remains and a later
cancellation may win the T035 terminal transition. No completion overwrites
that terminal state. A cancelled/terminal run cannot resume even if COMPLETED;
read-only inspection may still expose the stored outcome. A crash after effect
commit but before checkpoint update replays from business COMPLETED, not the
mock action. Checkpoint approval/result fields never substitute for these
checks. FAILED is terminal for this mock action, not RETRY/REPLAN eligible;
existing read-only capability retry/replan budgets remain unchanged.

Required evidence (future implementation, not planning tests):

| Task | Required contract evidence |
|---|---|
| T081 | Upgrade/downgrade and coexistence with TaskPilot and LangGraph tables; UUID/FK RESTRICT, named CHECK, unique and index behavior; invalid ranges/enums/JSON/state-field combinations; canonical proposal and outcome byte limits. |
| T082 | Same-tenant create/read/decision; cross-tenant 404 and in-tenant insufficient-role 403; active owner/admin only; forged actor/role rejected; immutable proposal; create/reuse and approve-vs-reject under independent PostgreSQL sessions; first decision wins and every duplicate decision conflicts; sanitized API/log output. |
| T083 | L0/L1 auto-allow; L2 approval before effect; L3/unknown/malformed classifier input produces no approval/effect; no Task/TaskRun enum change or authority in AgentState; the exact pending-reference checkpoint shape; checkpoint write must succeed before WAITING_APPROVAL; replay after approval commit/checkpoint failure reuses the same row; rejected, malformed, missing, and stale checkpoint cases fail closed through T035 without overwriting a terminal winner. |
| T084 | Exact tenant/run/approval/checkpoint/proposal match; approved mock success and bounded deterministic failure; duplicate delivery returns stored COMPLETED/FAILED without re-execution; NOWAIT contention returns bounded busy/conflict; rollback before commit and replay after commit/before checkpoint; cancellation before/after effect under independent sessions; stale identity-map reads; one committed outcome and no real external effect. |

Worker delivery is simulated by duplicate internal calls, not a new worker
implementation. These database/race tests are required for implementation
acceptance, not run during this documentation-only planning task.

## Consequences and deferrals

A new approval table and migration are required. Existing Task/TaskRun enums,
T035 lifecycle ownership, retry/replan budgets, checkpoint identity, and
Phase 5 deterministic context contracts remain unchanged. Generic policy/rule
DSLs, workflow engines, distributed locks, workers, credentials, real external
effects, and UI are deferred.
