# ADR-010 — Phase 8 deterministic Evaluation contract (Proposed)

Status: Accepted / frozen; Phase 8 Planning Strong Review APPROVED  
Date: 2026-09-25  
Scope: planning only; no runtime authority, persistence, or implementation

## Decision and authority boundary

Evaluation is observational regression evidence. It measures already-authoritative behavior and never decides tenant identity, membership/RBAC, Task or TaskRun lifecycle, risk, approval, checkpoint validity, runtime permission, business results, or observability truth. The business database remains business truth; checkpoints remain recovery state; telemetry remains observation. Evaluation can report mismatches but cannot mutate or override those sources.

## Versioned suite and the planning gate

The V1 suite is `suite_id = "taskpilot.phase8.v1"` and `suite_version = 1`. Every case has a stable `case_id` and `case_version = 1`. Inputs and expected values are JSON-compatible scalars, arrays, and objects. Each canonical case input is UTF-8 and at most 32 KiB. Changing fixture meaning requires a new case or suite version.

T100 is the Phase 8 Evaluation architecture/planning gate. Planning Strong Review is APPROVED; T100 is COMPLETE / APPROVED, and implementation begins at T101. T100 is not an implementation task.

## V1 case set

The V1 suite contains exactly five cases:

1. `deterministic.fixture_baseline` — the repository-backed deterministic capability contract in T101;
2. `recovery.retry_then_pass`;
3. `recovery.replan_then_pass`;
4. `approval.l2_requires_approval`;
5. `approval.l3_blocked`.

The earlier tabular/sum wording was pre-planning intent and is not an existing product capability. No tabular or sum capability is added for Phase 8.

## Deterministic baseline case contract

`deterministic.fixture_baseline` has `case_version = 1` and the exact bounded input:

```json
{"title":"Phase 8 deterministic fixture baseline","description":"Execute the repository deterministic fixture capability."}
```

The fixture supplies one validated `PlanStep` with `position = 1` and `instruction = "Return the deterministic fixture."`, selects the server-wired capability name `deterministic_fixture`, and uses its existing metadata (`action_version = "1"`, `risk_level = "L0"`, `read_only = true`, `deterministic = true`, `side_effect_free = true`). The expected `ExecutionResult` is `step_position = 1`, `success = true`, and exact output `deterministic-read-only-fixture:v1`. The expected verifier verdict is `PASS`.

Required evidence codes are the ordered set `capability_selected`, `execution_succeeded`, `output_exact`, `verification_passed`. A case PASS requires the exact input and dispatch, the exact successful result and verifier verdict, and every required evidence code. A case FAIL is a bounded assertion mismatch. A case ERROR is an inability to produce or validate the bounded case result (including an unexpected runtime/provider failure); raw exception/provider payloads are never evidence.

The remaining case tags and required evidence are fixed for metric calculation: `recovery.retry_then_pass` requires `retry_observed` and `recovery_pass`, and PASS means a bounded retry is observed before the final case PASS; `recovery.replan_then_pass` requires `replan_observed` and `recovery_pass`, and PASS means a bounded replan is observed before the final case PASS; `approval.l2_requires_approval` requires `approval_required`, `approval_satisfied`, and `execution_succeeded`, and PASS means the first attempt waits at the server approval boundary without capability execution, then a valid approval resumes the case and permits the expected execution; `approval.l3_blocked` requires `blocked_before_execution`, and PASS means the L3 route is blocked before capability execution. Missing or unsatisfied codes make the case fail or error under the case-result contract.

The remaining four cases use the existing Planner/Executor/Verifier, retry/replan, capability/context, and approval primitives. All five cases are provider-free and bounded.

## Case-result contract

Each produced result has exactly these required fields:

```json
{
  "case_id": "deterministic.fixture_baseline",
  "case_version": 1,
  "status": "pass",
  "evidence_codes": ["capability_selected", "execution_succeeded", "output_exact", "verification_passed"],
  "failure_code": null
}
```

`status` is one of `pass`, `fail`, `error`. `failure_code` is `null` for `pass`, is exactly `assertion_failed` for `fail`, and is one of `case_error` or `invalid_result` for `error`. No other failure code is valid in V1. `case_id` is 1–64 UTF-8 bytes and `case_version` is a non-negative integer. `evidence_codes` contains 0–16 unique codes, each 1–64 UTF-8 bytes, in lexicographic order. The suite contains at most five case results, ordered lexicographically by `case_id`, then numerically by `case_version`.

## Exact metric contracts

All four metrics use this same JSON shape:

```json
{"status":"ok","numerator":4,"denominator":5,"rate":"0.8000"}
```

`status` is `ok` or `not_applicable`; `numerator` and `denominator` are non-negative integers; `rate` is a fixed-precision decimal string or `null`. For a non-zero denominator, `0 <= numerator <= denominator`, `status = "ok"`, and `rate` is the quotient rounded with `Decimal` `ROUND_HALF_UP` to exactly four fractional places (for example, `1/3` is `"0.3333"`). For a zero denominator, the only valid value is `{"status":"not_applicable","numerator":0,"denominator":0,"rate":null}`. Rates are computed from integer counts using the standard library `decimal.Decimal`; binary floating-point serialization is not used.

- **`pass_rate`**: denominator is every case result produced by the run; numerator is results whose final status is `pass`. `fail` and `error` remain in the denominator. A run with no valid case results uses the zero-denominator value.
- **`recovery_success`**: applicable only to executed cases tagged `retry-then-pass` or `replan-then-pass`; denominator is those executed recovery results; numerator is results with status `pass` and every required recovery evidence code satisfied by that case contract. `fail` and `error` remain in the denominator. No applicable case is `not_applicable`.
- **`approval_compliance`**: applicable only to executed `L2 approval-required` and `L3 blocked` cases; denominator is those executed approval/safety results; numerator is results that pass the exact expected approval/risk contract. L2 requires the frozen approval boundary behavior; L3 requires the frozen blocked behavior. `fail` and `error` remain in the denominator. No applicable case is `not_applicable`.
- **`evidence_completeness`**: denominator is every produced case result whose contract defines one or more required evidence codes; numerator is results for which every required code is present and satisfied. Partial evidence is not in the numerator; `error` remains in the denominator when required evidence is defined. No applicable case is `not_applicable`.

## Exact machine report contract

T104 emits one canonical `taskpilot.eval.report/v1` JSON object with these required top-level fields and values:

```json
{
  "schema":"taskpilot.eval.report/v1",
  "suite_id":"taskpilot.phase8.v1",
  "suite_version":1,
  "runner_status":"completed",
  "cases":[
    {"case_id":"approval.l2_requires_approval","case_version":1,"status":"pass","evidence_codes":["approval_required","approval_satisfied","execution_succeeded"],"failure_code":null},
    {"case_id":"approval.l3_blocked","case_version":1,"status":"pass","evidence_codes":["blocked_before_execution"],"failure_code":null},
    {"case_id":"deterministic.fixture_baseline","case_version":1,"status":"pass","evidence_codes":["capability_selected","execution_succeeded","output_exact","verification_passed"],"failure_code":null},
    {"case_id":"recovery.replan_then_pass","case_version":1,"status":"pass","evidence_codes":["replan_observed","recovery_pass"],"failure_code":null},
    {"case_id":"recovery.retry_then_pass","case_version":1,"status":"pass","evidence_codes":["retry_observed","recovery_pass"],"failure_code":null}
  ],
  "metrics":{
    "approval_compliance":{"status":"ok","numerator":2,"denominator":2,"rate":"1.0000"},
    "evidence_completeness":{"status":"ok","numerator":5,"denominator":5,"rate":"1.0000"},
    "pass_rate":{"status":"ok","numerator":5,"denominator":5,"rate":"1.0000"},
    "recovery_success":{"status":"ok","numerator":2,"denominator":2,"rate":"1.0000"}
  },
  "comparison":{"status":"not_requested","reason":null}
}
```

`runner_status` is `completed` when all cases planned for that run produce `pass` or `fail` results and none is `error`; `partial` when the run continues but at least one planned case is `error`; `error` when the runner cannot produce a valid suite execution/report at all. The full V1 run plans all five cases; the T106 smoke run may plan its documented three-case subset. `cases` is the ordered case-result array. `metrics` always contains exactly the four names `pass_rate`, `recovery_success`, `approval_compliance`, and `evidence_completeness`, each using the shared metric shape; a zero denominator is represented as `not_applicable`, never by key omission or numeric zero rate.

`comparison` is always present with `status` and `reason`. `status` is `not_requested`, `comparable`, or `incomparable`; `reason` is `null` for the first two and one of `suite_id_mismatch`, `suite_version_mismatch`, `case_set_mismatch`, or `case_version_mismatch` for `incomparable`. Metrics belong to the individual run. An incomparable comparison emits no cross-run metric deltas and is not itself a metric failure.

Absent-vs-empty is explicit: required keys are always present; `null` is used only where this contract says no value applies; an empty array is a valid collection with zero members; key absence has no second meaning. Case IDs, evidence codes, and arrays use the bounds above. No raw secret, credential, provider response, checkpoint, authorization object, or unrestricted context enters the report.

Canonical serialization is UTF-8 JSON with lexicographically sorted object keys, the deterministic array orders above, compact separators `(',', ':')`, and exactly one trailing newline. No timestamp or run UUID is emitted. The complete UTF-8 artifact, including that newline, is at most 32 KiB for V1. If serialization would exceed that bound, T104 emits no oversized artifact and returns the bounded terminal condition `report_size_exceeded`.

## Comparison, runner, and deferred scope

Comparison is a separate cross-run decision. Every valid run still has its own metrics; suite/case mismatches do not turn the run into a metric failure. The runner is an in-memory local Python/test boundary with mocked providers and no network, paid model, SaaS, or database.

Deferred: live LLM-as-judge, remote Evaluation SaaS, generic benchmark or experiment tracking, Evaluation persistence/database, dashboard/UI, workers, analytics platform, billing, subjective production gating, and generic provider/model benchmarking.
